Implementation plan

Plan create & execution

A design for capturing reusable financial policy, solving it against point-in-time balances, and producing a durable chronological checklist through plan execute <plan-id>.

1. Core decisions

Primary design principle A plan is reusable policy. A plan run is an immutable point-in-time solution.

The plan stores user intent and reusable rules. A run stores the balance snapshot, generated steps, expected final balances, and diagnostics. Editing a plan or refreshing Plaid balances must not rewrite a previously generated run.

Money

Convert provider amounts into signed i64 cents at the integration boundary. Do not perform financial calculations with f32.

Determinism

Give rules explicit stages and positions so identical policy plus identical balances produces identical steps.

Atomicity

Validate and save a complete plan in one database transaction. Generate and save a run in a separate transaction.

Explainability

Every generated step references its source rule and includes the reason it exists.

Validation boundary

A plan can be structurally valid but infeasible today. Creation rejects malformed or contradictory policy. Execution reports insufficient current funds, ambiguity, or provider-data problems without corrupting the saved policy.

3. Proposed domain and persistence model

Plan (reusable policy)
 ├── Asset balance constraints
 ├── Liability payment rules
 └── Excess allocation rules

PlanRun (immutable solution)
 ├── Captured account balances
 ├── Ordered generated steps
 ├── Projected final balances
 └── Diagnostics

Plans and policy rules

  • Add updated_at and optionally status: Draft | Active | Archived to plans.
  • Add position and requirement: Required | BestEffort to applicable rules.
  • Make plan_id, destination account IDs, and required payment source IDs non-null.
  • Use i64 for every cents and basis-points value.
  • Add unique indexes for one balance rule per plan/account and one liability rule per plan/account unless multiple rules are intentionally supported.
  • Enforce at most one remainder allocation per plan.

4. plan create workflow

Use an interactive wizard backed by a transport-independent input structure. The wizard gathers data; a plan service validates and persists it.

struct CreatePlanInput {
    name: String,
    plan_type: PlanType,
    asset_rules: Vec<AssetRuleInput>,
    liability_rules: Vec<LiabilityRuleInput>,
    allocation_rules: Vec<AllocationRuleInput>,
}
  1. Load linked accounts and normalize account capabilities.
  2. Ask for the plan name and type.
  3. Select eligible funding accounts.
  4. Collect protected minimum balances for asset accounts.
  5. Collect liability target/fixed-payment rules and payment sources.
  6. Collect fixed, percentage, and remainder excess allocations.
  7. Display a normalized summary including implied stage order.
  8. Validate the complete input.
  9. On confirmation, save the plan and all rules in one transaction.

Creation-time validations

  • Referenced accounts exist and have compatible account kinds.
  • Exactly the fields required by each rule discriminator are populated.
  • Money values are nonnegative and percentages are between 0 and 10,000 basis points.
  • Percentage allocations total no more than 100%.
  • At most one remainder rule exists.
  • Every required liability rule has a funding source.
  • Duplicate plan/account rules are rejected unless explicitly supported.
  • Unallocated remainder is either retained deliberately or assigned to a destination.

5. Solver semantics

The MVP does not require a general optimization package. It requires deterministic simulation using integer cents and explicit priorities.

Stage order Protect reserves → required fixed payments → liability targets → fixed excess allocations → percentage allocations → remainder.
  1. Load the captured balances into an in-memory account-state map.
  2. Calculate spendable funds after protecting each asset minimum.
  3. Apply required fixed payments in position order.
  4. Apply target-balance liability payments in position order, capped at the current liability balance.
  5. Apply best-effort rules if funds remain.
  6. Capture the excess-allocation base.
  7. Apply fixed allocations.
  8. Calculate all percentages from the same captured allocation base, not a shrinking balance.
  9. Apply the single remainder rule or explicitly retain the remainder.
  10. Convert state transitions into chronological steps and projected final balances.

Post-solve invariants

Replay the generated steps against the snapshot before saving and assert that:

  • No source account falls below a required minimum.
  • No payment exceeds the remaining liability balance.
  • Every required target is satisfied for a feasible run.
  • Total outgoing value never exceeds total eligible value.
  • The replayed balances exactly equal the reported projected final balances.
  • Step sequences are unique, contiguous, and deterministic.

6. plan execute <plan-id> workflow

  1. Load and validate the active plan policy.
  2. Fetch live account data and convert all monetary values to cents.
  3. Capture the balance snapshot and the policy version/hash.
  4. Run the deterministic solver.
  5. Replay and verify the solution.
  6. Atomically save the run, snapshots, steps, diagnostics, and projected balances.
  7. Print the saved steps—not a separately recomputed representation.

If a required rule cannot be satisfied, persist an infeasible run with diagnostics but no misleading executable checklist. A later command may support an explicit best-effort mode.

7. Delivery phases

Phase 1

Formalize the domain

Document rule meanings, hard/soft behavior, funding eligibility, stage order, percentage base, and insufficient-funds behavior. Add pure Rust input and validation types.

Phase 2

Harden persistence

Add versioned migrations, correct relation cardinality, non-null foreign keys, integer widths, unique indexes, positions, and rule constraints.

Phase 3

Build plan creation

Implement the interactive wizard, summary/confirmation screen, service-level validation, and transactional save.

Phase 4

Implement the pure solver

Accept policy plus snapshots and return either a verified solution or structured diagnostics. Cover it heavily with table-driven tests.

Phase 5

Persist and display runs

Add run entities, snapshot capture, atomic persistence, chronological rendering, and a command to inspect historical runs.

Phase 6

Completion tracking

Allow steps to be marked completed/skipped and reconcile actual balances. Defer automatic money movement until the manual workflow is trustworthy.

Minimum test matrix

  • Exact funds, excess funds, and insufficient funds.
  • Multiple funding accounts with protected minimums.
  • Fixed payment greater than the remaining liability.
  • Already-satisfied target balance.
  • Fixed plus percentage plus remainder allocations, including rounding cents.
  • Invalid percentages, duplicate remainders, missing accounts, and incompatible account types.
  • Deterministic results regardless of database query order.
  • Historical run output remains unchanged after policy edits and balance refreshes.

MVP completion criteria

  • plan create produces no partially saved plans.
  • Invalid rule combinations cannot enter active persisted policy.
  • plan execute <id> creates a reproducible run from a timestamped balance snapshot.
  • Every feasible run has verified, ordered steps and projected final balances.
  • Every infeasible run explains which hard rules failed and by how much.
  • All calculations use integer cents and deterministic rounding.

This plan intentionally separates manual execution guidance from future automated transfers. The stored step model can support automation later without coupling the initial solver to provider-specific transfer APIs.
